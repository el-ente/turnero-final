# Reliability Review — 2026-08-24

Independent SRE audit of Turnero. Scope: observability, error handling, deploy safety, test coverage as a reliability signal, Firestore operational risk, abuse/cost exposure on public endpoints, incident readiness. Code-only findings, no changes made.

Baseline since `docs/app-review-2026-08-04.md`: RBAC/auth landed (`functions/src/middleware/auth.ts`), Firestore rules are no longer allow-all/date-bombed, `adminService` now has tests, `handleNoShow`/`finishTurn` transactions are properly atomic. The gaps below are what's left.

## Prioritized findings

### 1. CI never runs the test suite — deploy to prod is build-only
**Problem**: `.github/workflows/deploy.yml` and `preview.yml` run `pnpm -F app build` and `pnpm -F functions build`, never `pnpm -F functions test`. There is no third workflow that does. The `firebase.json` functions `predeploy` hooks also only run `lint` and `build` (`firebase.json:16-17`). CLAUDE.md tells humans to run tests before pushing, but nothing enforces it.
**Why it matters**: 106 passing tests exist (`functions/src/__tests__/`, verified green) but they're purely advisory. A broken test — including a regression in `adminService`'s cascade-delete logic or the ratio-based dispatch algorithm — does not block a merge to `main`, and `main` auto-deploys straight to prod (`deploy.yml:1-2`, prod gated only by human reviewer approval, not by any automated check). The tests are a false sense of safety: they look like a quality gate but function as documentation.
**Effort**: small. Add a `test.yml` workflow triggered on PR/push running `pnpm -F functions test`, and/or add `pnpm --prefix functions run test` to the `predeploy` array in `firebase.json` so a failing suite blocks `firebase deploy` itself.

### 2. No error tracking or alerting — a prod exception is invisible unless someone goes looking
**Problem**: Every controller catches errors and calls `logger.error(...)` (`firebase-functions` structured logger → Cloud Logging), e.g. `functions/src/controllers/turnController.ts:26,54,79`, `terminalController.ts` (6 call sites), `middleware/auth.ts:92`. That's it — no Sentry/Crashlytics/Error Reporting integration, no Cloud Monitoring alert policy in the repo, no notification channel configured anywhere in `firebase.json` or `.github/workflows/`.
**Why it matters**: this is the single biggest observability gap. If `createTurn` starts throwing for every request at 2am (bad deploy, Firestore quota, expired index — see #4), nothing pages anyone. The only way to find out is a customer complaint or someone proactively tailing `firebase functions:log`. Cloud Functions gen2 does export logs/errors to Cloud Error Reporting automatically by virtue of using `firebase-functions` `logger`, but with zero alert policies attached that just means the errors sit in a GCP console nobody watches.
**Effort**: small-medium. Minimum viable: one Cloud Monitoring alert policy per env on Cloud Functions error rate / log-based metric matching `severity>=ERROR`, routed to email/Slack. Medium: wire actual Sentry (has a Cloud Functions Node integration) for stack traces + grouping.

### 3. Public, unauthenticated endpoints have no rate limiting, no App Check, no per-caller cap
**Problem**: `createTurn`, `getCurrentTurn`, `cancelTurn` (`functions/src/controllers/turnController.ts`) are `onRequest({cors: true}, ...)` with no `requireRole` wrapper — by design (Totem/kiosk and the public `/mi-turno` link need to work without login). `cors: true` reflects *any* origin, so these aren't even restricted to the app's own domain — any external page's JS can call them directly. There's no App Check, no IP/token bucket, no CAPTCHA. The only "dedupe" is `createTurn`'s check for an existing active turn with the *same* `memberNumber`+`queueId` (`functions/src/services/turnService.ts:19-27`) — trivially bypassed by incrementing `memberNumber` on each call, since it's fully client-supplied with no ownership check (just `1 <= n <= 99999`, `turnService.ts:10-11`).
**Why it matters**: this is an availability/cost question, not an authz one. `setGlobalOptions({maxInstances: 10})` (`functions/src/index.ts:21`) caps concurrent blast radius somewhat, but a scripted client can still sustain up to 10 concurrent instances writing to Firestore continuously for as long as it wants — each `createTurn` call does 3 reads + 1 write minimum. Sustained abuse either runs up the Firestore/Functions bill or starves the 10-instance pool so real totem/web users get queued/rejected during the attack. This is a distinct risk from the security framing (who can write what) — it's "can a stranger degrade or bill this system without any account."
**Effort**: medium. Firebase App Check (reCAPTCHA v3 for web) on these three functions is the standard fix and is close to a config-only change given Firebase Auth is already wired into the app. A cheaper stopgap: a per-IP or per-`memberNumber` rate limit (Firestore-backed counter, or a Cloud Armor policy in front of the functions).

### 4. Composite Firestore indexes required by production queries aren't declared as code
**Problem**: `firestore.indexes.json` is empty (`"indexes": []`) and has been untouched since the initial commit (`git log` shows only `38af429 initial commit` ever touched it), while multiple service-layer queries require composite indexes to run at all in production Firestore:
- `turnService.ts:19-24` — `memberNumber ==` + `queueId ==` + `status in [...]`
- `turnService.ts:40-45` — `memberNumber ==` + `status in [...]` + `orderBy(createdAt desc)`
- `queueService.ts:6-9` and `:21-24` — `queueId ==`/`queueId in` + `status ==` + `orderBy(queuedAt asc)`
- `terminalService.ts:259-262` — `queueId ==` + `status ==` + `orderBy(queuedAt asc)` (inside the no-show requeue transaction)
- `adminService.ts:159-160` — `queueId ==` + `status in [...]`

These queries only work today because someone manually clicked "create index" in the Firebase console (likely against the original single `turnero-60150` project) at some point, or Firestore auto-suggested and it was accepted. None of that is captured in `firestore.indexes.json`, so it isn't deployed by `firebase deploy` and isn't reproducible.
**Why it matters**: this is exactly the kind of fix from `my-work.md`'s "long tail" that can regress silently — it's undocumented, has no CI check, and the failure mode (`FAILED_PRECONDITION: The query requires an index`) only surfaces the first time the query actually runs on an environment missing it. Concretely: were these indexes ever created on `turnero-1212-dev`/`qa`/`prod` after the 3-project split in the multi-env migration? If not, `getCurrentTurn`, the no-show requeue path, or `getWaitingTurns` will throw in production the first time they're hit, and it'll look like a random 500, not an infra gap — because nothing logs "missing index" distinctly from any other Firestore error at the call sites (just the generic `logger.error("Error getting current turn:", error)`).
**Effort**: small. Run each query once per env (or `firebase firestore:indexes` in GCP console) to capture current state, commit the real `firestore.indexes.json`, and let `firebase deploy` manage them going forward like every other artifact.

### 5. Real-time Firestore listeners have no error handler — silent failure on every live view
**Problem**: every `onSnapshot(...)` call across the app (`PublicDisplay.tsx:42,49,56`, `TerminalView.tsx:37,52,66`, `TerminalSelector.tsx:15`, `WebTicketView.tsx:64,88`) passes only a success callback, no error callback (the SDK's second/third argument). If a listener errors — permission-denied after a rules change, a transient index issue, an expired/revoked auth token, sustained network loss — the callback simply stops firing. The UI keeps showing its last-known state; nothing tells the user or an operator that data has gone stale.
**Why it matters**: `PublicDisplay` is the unattended waiting-room screen — it can run for a full business day with nobody watching the browser tab. If its listener dies (e.g. an auth token silently expiring after hours-long uptime, or a rules deploy briefly denying reads), the board freezes showing the last-called number indefinitely, and the only way anyone notices is a customer complaint at the counter. Same failure mode on `TerminalView`'s current-turn listener — an operator could keep working off a stale queue state without any indication the connection is dead.
**Effort**: small. Add an error callback to each `onSnapshot`, log it (see #2 for where those logs should go — client-side, so this needs either a lightweight client error-reporting call or at minimum a visible "connection lost" banner + auto-retry).

### 6. No Firestore backup / PITR configured
**Problem**: no mention of Point-in-Time Recovery, scheduled exports, or backup policy anywhere in the repo (`firebase.json`, `my-work.md`, or any doc). Default Firestore has no automatic backups unless explicitly enabled per-database.
**Why it matters**: combined with #4's data-corruption bugs already on file in `docs/app-review-2026-08-04.md` (turn-numbering collisions, non-atomic paths) and the fact that every write goes through `db.collection(...).update()`/`transaction` calls with no soft-delete anywhere (cascade deletes in `adminService.ts` are real `batch.delete()`s) — there is currently no way to recover from a bad admin action (e.g. wrong sector cascade-deleted) or a bug that corrupts turn data, other than "it's gone." This is a pure availability/DR gap, distinct from the correctness bugs themselves: even a *known, well-understood* bug that ships to prod for a day has no recovery path except manual data reconstruction.
**Effort**: small. Enable Firestore PITR (7-day continuous backups) per environment — config-only, no code change, in the GCP console or via `gcloud firestore databases update --enable-pitr`.

### 7. No audit trail for admin/staff actions
**Problem**: no `audit`/`history`/`activityLog` collection or equivalent anywhere in `functions/src` or `shared/src` (confirmed via search). Admin CRUD (`adminController.ts` — sector/queue/terminal create/update/delete) and staff actions (call/start/finish/no-show/recall) only ever mutate the current-state documents; nothing records who did what, when.
**Why it matters**: incident readiness. If a sector's queues disappear, or a terminal's config silently changes, or turn counts look wrong at end-of-day, there is currently no way to answer "who changed this and when" — you're limited to whatever happens to still be in Cloud Logging's default retention (30 days) via the sparse `logger.error` calls, which only fire on *failures*, not on successful mutations. There's no successful-write audit log at all.
**Effort**: medium. A `logger.info` call with structured fields (uid, action, target doc id) at the top of each mutating service function is the cheap version; a dedicated `auditLog` Firestore collection written transactionally alongside the mutation is the durable version.

### 8. Test coverage still has gaps in the highest-complexity, highest-blast-radius code path
**Problem**: per `docs/app-review-2026-08-04.md`, `getNextTurnRatioBased` (`terminalService.ts:32-88`, one Firestore read per active queue on every "next turn" click, the most algorithmically dense function in the codebase) was flagged as having zero test coverage. Worth re-verifying at fix time — `terminalService.test.ts` is now 791 lines, so this may already be addressed; if not, it remains the top test-coverage gap because it's staff-facing on every single terminal interaction, not an edge case.
**Why it matters**: as a reliability signal, not a QA nicety — this is the function every operator hits every time they pull a new customer. A silent regression here (e.g. ratio math going wrong, or an infinite loop across queues) degrades every terminal simultaneously, and nothing but the tests would catch it before prod given finding #1.
**Effort**: small (verify current state first — may be a non-issue now).

### 9. No documented runbook or on-call path
**Problem**: `README.md` has no incident/troubleshooting/on-call section (grepped, zero hits). Two "how do we recover" playbooks worth having don't exist anywhere: (a) bad deploy rollback — Firebase Hosting has one-click rollback to a previous release via console/`firebase hosting:clone`, and Cloud Functions gen2 can be rolled back by redeploying a previous git ref (there's no function-level traffic-split/rollback API exposed via the CLI used here), but none of this is written down; (b) "prod is throwing 500s, now what" has no documented first step (check Cloud Logging → check which controller → check #4's missing-index theory, etc.).
**Why it matters**: given findings #1-#2, when something does break in prod, response time is entirely a function of one person's tribal knowledge of the codebase. A one-page runbook (where to look, common failure signatures like `FAILED_PRECONDITION` = missing index, how to roll back hosting vs. functions) turns a cold debugging session into a checklist.
**Effort**: small — this is a documentation task, not code.

## Lower-priority / worth noting

- `functions/src/index.ts:21` sets only a global `maxInstances: 10` — no per-function tuning (e.g. admin CRUD could have a much lower cap than `createTurn`), and no `minInstances`, so every function pays a cold-start on the first request after idle. For a totem in continuous use this is probably fine; worth checking cold-start latency on `createTurn` specifically since that's the customer-facing critical path.
- `AdminView.tsx` catch blocks (e.g. `:71-73`, `:86`) swallow the actual error object into a generic toast string ("Error cargando datos") with no `console.error`/logging of the underlying error — makes reproducing an admin-reported bug harder than it needs to be, since the real error never leaves the browser tab that hit it.
- `functions/package.json` `engines.node: "24"` — confirm the exact Cloud Functions gen2 runtime support window for Node 24 per environment before it becomes the thing that breaks a future redeploy if GCP's supported runtime list changes.
